# Быстродействие и измерения

## Обычная работа

Модель получает инструкцию объединять native tool calls, если аргументы известны.
Агент выполняет их последовательно с прежними проверками. Зависимый шаг выбирается
после результата. Снимки рекомендуются на границах этапов и по запросу пользователя;
числовые изменения подтверждаются `get_dimension`.

`Provider.complete` получает исходную локальную историю и создаёт отдельную
проекцию для модели: прежние CAD-снимки заменяются последним набором, повторные
деревья — точными дельтами. Требования, пользовательские чертежи, аргументы и ID
инструментов сохраняются. Ошибки и неуспешные проверки остаются целиком.
Полная локальная история и свидетельства проверки не сокращаются.

`features_observation=N` задаёт полный массив. `features_delta` указывает номера
`base` и `id`; к предыдущему массиву применяются `edits` в порядке убывания
`start`: удалить `delete` элементов, вставить `insert`. Сохраняются порядок,
удаления и повторяющиеся элементы без модельного пересказа.

В изображениях для модели обрезаются только полностью белые/прозрачные внешние
поля с отступом не менее 8 пикселей. Производная — PNG без масштабирования;
используется, только если стала меньше. Принятый оригинал без метаданных доступен
в истории и скачивании. CAD-снимки остаются 400×300 без дополнительной обрезки.
Производные кэшируются в пределах провайдера, каталог MCP — его сессии.

UI применяет SSE по `seq`. Snapshot нужен при открытии, пропуске и восстановлении
связи. Heartbeat раз в 2 секунды подтверждает связь без истории; отсутствие
heartbeat 8 секунд запускает восстановление. Разрыв SSE останавливает новые CAD-шаги.

## Метрики

`GET /api/runs/{id}` содержит добавочное поле `metrics`:

- `model_calls`, `model_seconds` — число обращений и суммарное время модели;
- `cad_calls`, `cad_seconds` — инструменты, запрошенные моделью;
- `verification_calls`, `verification_seconds` — служебные независимые проверки;
- `request_bytes`, `image_count` — суммы байтов отправленных JSON-тел и числа
  переданных изображений по всем обращениям;
- `input_tokens`, `output_tokens`, `cached_tokens` — значения, сообщённые API.
- `cost` — сообщённый API расход; без него сумма остаётся `null`.

`model_metrics` содержит показатели отдельного запроса: подготовку тела, ожидание
слота, полный ответ. Байты включают base64/tools, но не заголовки/TLS. Токены берутся
только из API; если хотя бы один запрос не сообщил показатель, его сумма — `null`.
В непотоковом режиме `first_token_seconds=null`.
Диагностика не содержит кода, текстов, путей, картинок или ключей.

## Бенчмарк без CAD

Автономное сравнение пяти синтетических сценариев:

```powershell
$env:PYTHONUTF8='1'
.venv\Scripts\python.exe -m scripts.benchmark_performance --parallel-preparation --output .superpowers\performance-offline.json
```

Живое сравнение через сохранённый профиль и Credential Manager:

```powershell
.venv\Scripts\python.exe -m scripts.benchmark_performance --live --profile-id PROFILE_ID --repeats 3 --output .superpowers\performance-live.json
```

SolidWorks/MCP не запускаются. В паре одинаковы сообщения, tools, картинки и
reasoning; различается потоковый режим. Порядок true/false чередуется между
повторами. Отдельно сравниваются полный и компактный контексты. Три повтора по
пяти сценариям — 60 запросов API. Короткая проверка:
`--scenario dimension --repeats 1` (четыре запроса).

`--input PATH` читает JSON-массив `name/messages/tools` для воспроизведения истории.
В отчёт попадают только хеши входа, числовые метрики, число предложенных команд
и безопасные коды ошибок. Команды никогда не выполняются. Медиана/p90 вычисляются
по успешным запросам; p90 — ближайший ранг, при трёх повторах это максимум.
Неизвестный usage/расход остаётся null. Для устойчивого вывода нужны дополнительные
повторы с одинаковыми профилем, сценарием, reasoning и состоянием кэша.

`--effort low` сравнивает меньшую силу рассуждения без изменения сохранённого
профиля. Автоматическое снижение не включено: сначала сравниваются ошибки и
независимая проверка на одинаковых задачах. Байты не равны визуальным токенам.

## Экспериментальная подготовка

`--parallel-preparation` сравнивает последовательное и параллельное чтение трёх
изображений без tools. В обычных CAD-прогонах дополнительные запросы не включены:
сначала нужны замеры выгоды. Семафор Provider допускает максимум два одновременных
completion-запроса, включая основной. COM остаётся в одном STA.

`cadnext.preparation.prepare_images` возвращает предварительные наблюдения,
метрики и SHA-256 входа. Вызывающая сторона проверяет хеш перед использованием;
устаревшие заметки отбрасываются. Stop отменяет только подготовительные задачи.
Наблюдения не доказывают размеры и не становятся исполняемыми командами.

`Provider.complete(..., stream=True)` собирает SSE целиком, требует завершения
и проверяет native tool calls. Оборванный/некорректный поток — ошибка без частичного
исполнения. Обычный агент сохраняет непотоковый режим.

Python следует повторно использовать через проверенные фрагменты, например
из `docs/python-inspection.md`. Автоматический повтор старого кода не добавлен:
ошибка может оставлять частичные изменения. Следующая готовая заготовка выбирается
по частоте и времени ошибок в измерениях.

## Автономное сравнение 26.10.2026

60 запросов к фиктивному транспорту, медиана JSON-тела для stream=false:

| Сценарий | Полный, байт | Компактный, байт | Сокращение |
|---|---:|---:|---:|
| Листовая деталь | 21 829 | 10 438 | 52% |
| Изменение размера | 17 973 | 9 494 | 47% |
| Сборка | 17 982 | 9 503 | 47% |
| Python | 17 991 | 9 512 | 47% |
| Длинный диалог | 90 569 | 13 731 | 85% |

Это синтетическая история с повторными деревьями и снимками. Проценты не
прогнозируют ускорение реальной детали. Итоговая приёмка сравнивает полное время,
медиану/p90, число обращений, usage/расход и независимую проверку геометрии.

## Живое сравнение DeepSeek 26.10.2026

Профиль `Ikhdev`, `deepseek-v4.1-flash-1017`, сохранённый `reasoning_effort=max`.
60 запросов API без ошибок: пять синтетических историй, три повтора, четыре
конфигурации. Команды из ответов не выполнялись; SolidWorks/MCP не
использовались. Сначала выполнена отдельная проба из четырёх запросов.

Время полного ответа: **медиана / p90, секунды**. При n=3 p90 равен максимуму.

| Сценарий | Полный, JSON | Полный, stream | Компактный, JSON | Компактный, stream |
|---|---:|---:|---:|---:|
| Листовая деталь | 5,15 / 5,88 | 5,00 / 6,05 | 5,11 / 5,13 | 4,56 / 6,44 |
| Изменение размера | 5,87 / 6,06 | 5,56 / 7,23 | 4,32 / 5,53 | 4,23 / 4,46 |
| Сборка | 6,94 / 6,94 | 5,18 / 8,19 | 5,96 / 6,93 | 4,28 / 6,38 |
| Python | 6,38 / 8,59 | 7,92 / 8,81 | 6,98 / 8,07 | 7,58 / 10,67 |
| Длинный диалог | 4,95 / 6,50 | 4,36 / 5,25 | 3,89 / 5,48 | 4,42 / 4,43 |

Сообщённые API входные токены на запрос (полный → компактный): листовая деталь
3834 → 2226, размер 3513 → 2030, сборка 3508 → 2025, Python 3503 → 2020,
длинный диалог 16418 → 2890. Экономия контекста 42–82% подтверждена API, но время
не сократилось одинаково: Python в этой выборке стал медленнее. Длина сгенерированных
ответов и попадание в кэш различались. Устойчивого выигрыша stream во всех
сценариях нет; обычный агент сохраняет JSON/nonstream.

Медианы времени до первого фрагмента в потоковых конфигурациях составили
1,19–3,21 с. Они измерены отдельно от времени полного валидированного ответа;
ранний фрагмент не означает, что CAD-команда уже готова к исполнению.

Подготовка трёх изображений: последовательная 24,39 с, параллельная 15,69 с,
по три API-запроса и 900 входных токенов в каждом режиме. Выход: 3049 и 3754 токена
соответственно. Это одна пара, последовательный режим шёл первым, поэтому прогрев
и вариативность генерации могут влиять на разницу. Эксперимент остаётся отдельным
от обычных CAD-прогонов. API не сообщил `cost`; расход не оценивался по предположению.

Отдельно выполнено 12 успешных запросов сценария изменения размера с
`reasoning_effort=low`, три повтора на конфигурацию. Медиана/p90: полный JSON
5,00/6,07 с, полный stream 4,57/5,57 с, компактный JSON 4,71/5,41 с,
компактный stream 4,54/4,99 с. При компактном контексте это не быстрее медиан
`max` (4,32 и 4,23 с) в основной серии; состояние кэша и длины ответов отличались.
Сохранённый профиль не менялся. Уровень рассуждения автоматически не снижается.

Всего в этой приёмке: 82 живых completion-запроса — четыре пробных, 60 основных,
шесть подготовки и 12 с low. Проверка корректности геометрии в них отсутствует.

Полный числовой отчёт в локальном `.superpowers/sdd/2026-10-26-performance-implementation/live-report.json`.
Сравнение low — рядом в `live-low-report.json`.
Меньшее время ответа в этих историях не доказывает ускорение построения реальной
детали или сохранение качества инженерной геометрии; для этого нужны одинаковые
живые CAD-задачи с независимыми проверками.
