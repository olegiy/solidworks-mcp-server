# Последовательный агентский цикл

Задача 3 реализована в `cadnext/agent.py`. Приложение, HTTP/SSE и браузерный чат
добавлены в задаче 4 (см. `app.md`). Реальные CAD-операции в задаче 3 не выполнялись.

## Использование

`Agent` получает уже подключённый `SolidWorksMcp`. Подключением MCP и временем жизни
провайдера владеет вызывающее приложение. Все методы вызываются из одного event loop.

```python
agent = Agent(mcp)
run = agent.start(session_id=session_id, provider=provider, message=user_message)
await agent.wait(run.id)
snapshot = run.snapshot()
```

`start` сразу закрепляет единственный активный запрос; второй получает `AgentBusy`.
Профиль — неизменяемый снимок внутри провайдера. История диалогов хранится в памяти
агента по `session_id`, восстановление после перезапуска приложения пока не предусмотрено.
Передача другого профиля в следующем ходе сохраняет локальную историю, но новый
провайдер заново применяет свои ограничения приватности ко всем сообщениям.

`Run` содержит `id`, `session_id`, `profile_id`, `status`, `messages`, `events`,
`stop_requested`, `confirmation`, `call_count`, `max_calls`, `checks`, `verification`.
При известной ошибке `execute_python` также доступны `repair_attempts` и `repairing`.
Для API предназначен `snapshot()` — независимая копия данных без провайдера,
ключей, фоновой задачи и объектов синхронизации. Исходные тексты и локальные результаты
видны локальному интерфейсу; фильтрация применяется перед внешним HTTP-запросом.

## Модель и инструменты

Каталог извлекается через `mcp.tools()`. Имена и JSON Schema проверяются; неизвестные
инструменты, некорректные аргументы, NaN/Infinity и повторные ID вызовов останавливают
прогон до их исполнения. JSON Schema не загружает ссылки из сети.

При включённом цикле цели к каталогу добавляются только локальные
`cadnext_define_goal`, `cadnext_bind_requirements` и
`cadnext_report_visual_evaluation`; они не вызывают MCP и не расходуют CAD-бюджет,
но служебный вызов обязан быть единственным в ответе модели. Совпадение их имён с
каталогом MCP останавливает прогон.

Несколько native tool calls одного ответа выполняются последовательно. Их исходные
ID сохраняются в сообщениях `tool`. Фактический результат передаётся модели перед
следующим решением. Проверяющие вызовы вкладывают свои результаты в `verification.evidence`;
они не добавляются как неподтверждённые моделью tool calls в историю протокола.
Если пакет прерван, невыполненные вызовы получают явный ответ об остановке.

Модель получает инструкцию объединять действия с уже известными аргументами в один
ответ. Зависимый шаг выбирается после фактического результата. Снимки рекомендуются
на границах этапов (готовый эскиз, элемент, итоговая оценка) и по явному запросу;
числовые изменения сначала подтверждаются `get_dimension`. Проверки каждого
действия и резервирование лимита сохраняются.

Снимки остаются image-блоками: UI получает событие `image`, история — сообщение
с `data:image/...;base64,...`. Снимки уже завершённых вызовов сохраняются и при отказе
от последующего Python-кода. Провайдер передаёт их модели только при `vision` и,
для внешнего подключения, автоматическом разрешении передачи при старте Agent.
Изображение не подменяется текстом base64.

По умолчанию разрешено 80 MCP-вызовов на запрос; `max_calls` принимает 1–1000.
Служебные чтения до/после изменений учитываются в этом же счётчике. Перед мутацией
агент проверяет наличие нужных инструментов проверки и запас вызовов на всю проверку.
Каталог ограничен 256 КиБ, исходящая история и отдельный ответ модели — 8 МиБ;
лимиты можно задать в конструкторе. Ошибка контекста завершает прогон без fallback.

## Подтверждения и остановка

Данные передаются выбранному провайдеру без окна согласия. При старте Agent закрепляет
контекст за диалогом и профилем и разрешает передачу текста; снимки — только при
поддержке `vision`. Внешний текст по-прежнему маскируется.

Без сохранённого разрешения первый Python-код требует решения:

```python
agent.confirm(run.id, confirmation_id, approved=True)
```

`kind="python"` содержит точный код после восстановления локальных путей.
Кнопка «Разрешить постоянно» сохраняет общее разрешение приложения в `settings.json`
до выполнения кода. Оно действует для всех диалогов и подключений после перезапуска.
В настройках переключатель «Всегда разрешать выполнение Python» сохраняется сразу;
снятие флажка возвращает запрос разрешения перед следующим фрагментом.
Ошибка записи не разрешает код. `Agent(mcp, settings=store)` использует эту политику;
при создании Agent без SettingsStore сохранён совместимый режим разрешения в памяти
для пары диалог+профиль.
Модель не запрашивает разрешение обычным текстом: она вызывает `execute_python`,
а подтверждением управляет приложение. Перед каждым обращением к модели системная
инструкция обновляется по актуальному разрешению, включая старые диалоги и смену
настройки во время работы. При постоянном доверии модель получает явное указание,
что разрешение уже выдано. Прочтение чертежа кратко описывается без отдельного
согласования; уточнения нужны только для недостающих или противоречивых данных геометрии.
Отказ завершает прогон со статусом `rejected`. Устаревший, чужой или повторный ID
отклоняется. Python имеет доступ к системе и COM; песочницей этот механизм не является.

`stop(run.id)` запрещает новые действия. Если COM-вызов уже отправлен, статус
становится `stopping`; агент сохраняет его фактический исход и не вызывает readback
или следующий инструмент после остановки. Выполненное изменение не откатывается.
Если текущий вызов завершается таймаутом, итог остаётся `uncertain`, даже после stop.

`await agent.wait(run.id)` защищает рабочую задачу через `asyncio.shield`:
отмена браузерного ожидания не отменяет COM. Приватную задачу Run отменять нельзя.
`await agent.aclose()` запрещает новые запросы, останавливает текущий и ждёт его исход.

## Независимая проверка

| Действие | Что проверяется |
|---|---|
| `set_dimension` | Имя, единицы и фактическое значение через `get_dimension`; допуск 0,000001 мм/градуса |
| `create_sketch`, `cut_through`, `add_mate` | Возвращённое имя отсутствует до операции и присутствует в дереве после |
| `create_base_flange` | Новый элемент дерева и фактические толщина/радиус с учётом округления MCP до четырёх знаков |
| `create_part`, `create_assembly` | Новый документ в списке открытых документов и доступное дерево |
| `add_component` | Новый компонент с нужным путём, отсутствие подавления и присутствие в дереве |
| `save_document`, `export_flat_pattern_dxf` | Правильный путь, непустой файл и изменение размера/времени файла относительно состояния до вызова |
| Эскизная геометрия, закрытие эскиза, перестроение | Чтение дерева как свидетельство; точная геометрия остаётся `unverified` |
| `execute_python` и действия без независимого критерия | «Выполнено, результат требует проверки» |

Для дерева запрашивается до 1000 элементов. Если до создания достигнут этот предел,
агент прекращает прогон до мутации: полнота исходного дерева не подтверждена.
Проверка файла подтверждает запись, но не проверяет геометрию внутри SLDPRT/DXF.
Проверка дерева подтверждает наличие элемента, но не все его инженерные свойства.

`status="completed"` означает завершение цикла. Достоверность мутаций отражается
отдельно: `verification` принимает `not_required`, `verified`, `unverified`, `failed`.
Любое непроверенное действие сохраняет `unverified` у всего прогона. Модельный текст
не изменяет серверную отметку проверки. Ошибка readback сохраняется в истории
вместе с фактическим значением; повтор мутации не выполняется.

CAD-ошибка, включая вложенный `{status: "error"}`, обычно завершает прогон. Для
известного `CAD_ERROR` от `execute_python` агент может дать модели до двух попыток
исправления: предыдущий вызов не повторяется, модель получает номер строки и просит
read-only инспекцию с минимальным продолжением. Потеря MCP, повреждённый ответ и
COM-таймаут сохраняют неопределённый исход и блокируют новые запросы до перезапуска;
для них исправление не запускается. Undo и смены исполнителя нет.

Если известные неверные аргументы отклонены до доступа к CAD, ошибка содержит
`phase="preflight"` и `changes_started=false`. Модель получает эту фазу и подсказку:
допустим исправленный фрагмент целиком с необходимой подготовкой объектов, поскольку
ни одна его строка не исполнялась. Это не разрешает повторять действия предыдущих
вызовов. Для ошибок исполнения сохраняется инспекция и минимальное продолжение;
общий предел — две попытки исправления, неизвестный исход COM никогда не повторяется.

## События для интерфейса

`agent.events(run.id, after=seq)` — асинхронный генератор событий с полями
`seq`, `at`, `type`, `data`. Поддерживаются `message`, `tool_start`, `tool_result`,
`image`, `confirmation`, `repair`, `status`, `error`. Номера начинаются с 1.
Снимок и получение пропущенных событий не выполняют CAD-инструменты заново.
Медленный потребитель получает и события, добавленные во время его паузы.
Закрытие генератора активного прогона вызывает `stop`.

У мутации сначала появляется фактический `tool_result`, затем обновлённый результат
с независимой проверкой; интерфейсу следует обновлять запись по `tool_call_id`.
Проверяющие операции помечены `verification=True` и имеют собственные ID.
После завершения используются статусы `completed`, `stopped`, `failed`, `uncertain`,
`limit_reached`, `rejected`; во время работы — `queued`, `running`, `repairing`,
`awaiting_confirmation`, `stopping`.

Диагностический logger `cadnext.agent` пишет имя инструмента, длительность и статус.
Запросы, код, полные пути, ключи и изображения в диагностику не записываются.

## Цикл достижения цели

Цикл включён по умолчанию для CAD-задач и может быть явно отключён параметрами
запуска. Он не заменяет прежнюю проверку операций: `verification` по-прежнему
показывает достоверность отдельных CAD-действий, а `goal.outcome` — достижение
зафиксированных требований.

### Контракт и счёт

Перед первым изменением документа модель обязана вызвать локальный
`cadnext_define_goal` и зафиксировать не более 64 требований. У требования есть
уникальный ID, описание, источник (запрос или вложение), обязательность, целый вес
1–100, метод `cad` или `vision`, а для числового CAD-признака — ожидаемое значение,
допуск и единица `mm`/`deg`. Контракт неизменяем: его digest входит в каждое
доказательство, а изменение значений, весов или обязательности отклоняется.
`cadnext_bind_requirements` только связывает уже зафиксированные требования с
реальными именами созданных объектов; эталон он не меняет.

Первый критерий — «Схожесть с требованиями»: `score = 100 × сумма весов pass /
сумма весов всех требований`. Unknown и fail баллов не дают, знаменатель не
меняется. При пороге 100 (по умолчанию) должны пройти все требования. Порог ниже
100 может ослабить только необязательные признаки: любой обязательный fail или
unknown всё равно блокирует достижение. Отсутствие доказательства никогда не
превращается в pass.

### Доказательства

* CAD-размер перечитывается `get_dimension`; имя размера обязано совпасть с
  привязкой, единица — с требованием. Числовой статус вычисляет приложение из
  свежего `actual`; статус, который заявила модель, не принимается.
* Допуск по умолчанию — `1e-6` мм/градуса для размеров и `5e-5` мм для листовых
  данных. Пользовательский допуск имеет приоритет, но допуск строже точности
  чтения даёт `unknown`, а не тихое ослабление.
* Дерево доказывает только наличие имени, не геометрию, внутреннюю форму или
  корректность перестроения. Усечённое дерево делает отсутствие имени `unknown`.
  Список компонентов учитывает путь и подавление. Массовые свойства сравниваются
  только с явным числовым эталоном и требуют явного поля.
* Запрошенный файл проверяется по прежним правилам: путь совпадает, файл
  существует и не пуст. Если известна подпись «до», неизменившийся файл — fail.
* Визуальные признаки оценивает отдельный запрос к тому же Provider: эталонные
  изображения из вложений запуска, текущий снимок и CAD-факты. Модель возвращает
  ровно один `cadnext_report_visual_evaluation` с ID требований, `pass`/`fail`/
  `unknown`, объяснением и ссылками на реальные текущие `image_ids`. Свободный
  процент не участвует в счёте. Нет эталона или снимка — `unknown`. Vision-pass
  помечается как «Оценка модели» и не доказывает скрытую геометрию; authority
  итога — `cad`, `vision` или `mixed`.
* `revision` увеличивается перед любой потенциальной геометрической мутацией,
  включая `execute_python` и неуспешную попытку. Доказательство другой ревизии,
  другого контракта или другого активного документа не засчитывается. Это
  контроль действий приложения, а не защита от ручного редактирования вне его.

### Фазы и завершение

`goal.phase` проходит `preparing` → `executing` → `evaluating` → `correcting` →
`finished`. Ответ без tool calls не завершает CAD-цель: он запускает свежую
проверку. При `not_achieved` модели передаются только актуальные расхождения и
остаток бюджета. Лимиты по умолчанию: 10 оценок, 3 оценки без прогресса, 80
MCP-вызовов вместе с проверками и `4 × max_evaluations + 8` ходов модели. Повторная
оценка без новой ревизии не делает новых CAD-запросов, а завершает прогон
`no_progress`.

| Исход | `status` | `completion_reason` |
| --- | --- | --- |
| Все требования пройдены | `completed` | `criteria_met` |
| Исчерпан лимит оценок | `limit_reached` | `evaluation_limit` |
| Нет прогресса после исправлений | `limit_reached` | `no_progress` |
| Исчерпан бюджет CAD-вызовов | `limit_reached` | `call_limit` |
| Исчерпаны ходы модели | `limit_reached` | `model_turn_limit` |
| Недостаточно безопасных доказательств | `completed` | `evaluation_unavailable` |
| Нужны обязательные уточнения | `completed` | `clarification_required` |
| Справочный запрос | `completed` | `informational` |
| Stop/rejected/uncertain/failed | соответствующий | `stopped`/`rejected`/`uncertain`/`failed` |

Остановка, отказ, неизвестный исход COM и ошибка имеют приоритет над успехом.
`uncertain` блокирует новые прогоны до перезапуска. Две прежние попытки исправления
Python не сбрасываются оценками. Для execute_python успешный goal может оставаться
при `verification=unverified`: обе отметки показываются раздельно.

### Примеры

* `expected=50 мм`, `actual=50.0 мм`, допуск 0.01 → pass, 100%.
* `expected=50 мм`, `actual=49.0 мм` → fail; даже при визуально похожем силуэте
  итог не achieved.
* Размер не прочитан, привязки нет или ответ CAD усечён → unknown, не pass.
* Только визуальное подтверждение без CAD-факта по числовому требованию → unknown.

Универсального сравнения B-rep в первой версии нет: всё, что не покрыто
фиксированными CAD-чтениями, остаётся visual или unsupported. Собственный Python
модели не считается независимым числовым верификатором.

### Критерий → сбор состояния → оценка → исправление → завершение

| Критерий | Сбор состояния | Оценка | Исправление | Завершение |
|---|---|---|---|---|
| Схожесть результата с требованиями, «оценка результата» | Локально отсутствует: в `M` и `P` нет ни одного токена `evaluat*`, `score*`, `criteria*`, `goal*`, `similarit*`, `rubric*` (0 совпадений) | Выполняется не клиентом. Состояние прогона приходит с сервера: `GET /agent-runs/{id}` → `{id, status: string, …}`; локально `status` проверяется только как строка (`Io`), перечисление статусов неизвестно (`M` L20:C19957; валидатор `Io` — L20:C16270) | См. строку «Повтор»: `POST /agent-runs/{id}/rerun` | Порог, число итераций и признак успеха задаёт сервер; локального счётчика итераций нет |
| Классификация запроса (справочный/сборочный) | Текст, история (последние 8 реплик) и вложения отправляются на сервер (`M` L20:C20925) | Ответ `{available, intent, confidence, reason}`; при `confidence` ниже порога интерфейс предложение не показывает; при ошибке — `{available:false}` без локального fallback (`R` L1165:C6078) | Не предусмотрено — только предложение пользователю | Если сервер недоступен, классификация просто отсутствует |
| Допустимость изменения модели (policy) | Эффект кода вычисляется до запуска: `readOnly`, список использованных CAD-членов `findings[]`, `tableRevision`, `unknownMembers[]` (`M` L17:C60244 prepareCell, L17:C60326 prepareMacro) | Сравнение с политикой `agentExecutionPolicy` (`always`/`read_only`, `M` L17:C37044) и с решением пользователя | Отказ не повторяется автоматически; пользователь может одобрить один раз, до конца прогона или всегда (`M` L20:C46102) | Отказ терминален для команды: `read_only`, `declined`, `approval_timeout`, `cancelled` (`M` L20:C34145) |
| Выполнение не изменило документы (постусловие) | Отпечаток состояния документов до и после запуска клетки (`Se.runPrepared`) | При `policyViolation` формируется список изменений `{what, document}` (`M` L20:C48447 reportViolation) | Нет исправления: факт фиксируется телеметрией `fingerprint_violation` и уведомлением `policy_violation` (`M` L17:C56610) | Изменение не откатывается; прогон продолжается, пользователь уведомлён |
| Подтверждение мутации | Ожидание ответа на `agent:confirm` с дедлайном 30 с (`M` L20:C34145) | Ответы: `once`, `request`, `always`, `refuse`; таймаут = отказ | Повторного вопроса нет; при отказе клетка не выполняется | Таймаут и отказ завершают шаг без исполнения |
| Повтор (retry) | Сервер присылает `attempt_id` и счётчик `attempt` в записи фоновой задачи (`M` L20:C67661) | Сравнение фаз/попыток выполняет сервер; локально только отображение | Фоновые задачи: повтор с `action: resume` или `restart`; диалог: `POST /agent-runs/{id}/rerun` с необязательным сообщением и `effort` (`M` L20:C20774) | Локального предохранителя «нет улучшения N раз» и локального лимита попыток нет |
| Завершение прогона | Клиент получает `cad.cancel`, `run.release` или команду остановки от пользователя | Локально решается только «кто владеет» прогоном и занят ли SolidWorks: `cad.status` → `{exists, busy}` (`M` L20:C12578) | — | `endRun(runId, reason)`; причины: `stopped by the person`, `superseded by a new run`, `released by the service`, `cancelled before it started`, `ended by a stop that had to kill`, `signed out` (`M` L20:C37923) |

### Протокол, который удалось зафиксировать

* Транспорт — WebSocket поверх TLS (незашифрованный `ws:` допускается только для
  `localhost`), заголовки `Authorization: Bearer …` и `X-Mecagent-Resume`, предел кадра
  8 МиБ (`M` L20:C25718).
* Кадры: `authenticated`, `ready`/`status`, `ping`/`pong`, `result`, `result_ack`,
  `resume`/`resumed`/`resume_state`. Клиент сообщает возможности `session_resume_v1` и
  `ask_user_v1` (`M` L20:C26509, L20:C26891).
* Возобновление после разрыва: сервер присылает список `command_ids`; клиент отвечает
  `completed`/`running`/`unknown` и заново отправляет уже полученные результаты; повторы
  команд с тем же `command_id` не выполняются повторно (`M` L20:C27172).
* Команды исполняет клиент по полю `operation`: `run.acquire`, `run.release`, `cad.execute`,
  `cad.macro`, `cad.compile`, `cad.wait`, `cad.stop`, `cad.cancel`, `cad.status`, `cad.health`,
  `cad.artifacts`, `cad.output_path`, `user.ask`, `files.upload`/`files.download`,
  `session.close` (`M` L20:C12435…L20:C50169).
* HTTP: `POST /chat/sessions/{id}/agent-session`, `POST /agent-sessions/{id}/connection-ticket`,
  `GET /agent-sessions/{id}`, `GET /agent-runs/{id}`, `POST /agent-runs/{id}/cancel`,
  `POST /agent-runs/{id}/rerun`, `POST /agent-runs/{id}/artifacts/download`,
  `POST /agent/classify-intent`, `POST /chat/sessions/{id}/messages` (`M` L20:C19650, L20:C19957).
* IPC: 190 литеральных каналов и 137 обработчиков в главном процессе, один preload с 19
  экспортированными членами; единственная точка регистрации проверяет, что отправитель —
  главный фрейм окна приложения (`M` L3:C3016).

### Отдельно: наблюдаемое, вывод и неизвестное

Наблюдаемое (код и Evidence):

* Оценки схожести, счёта, критериев или порога в клиенте нет. `score` в интерфейсе относится
  к релевантности найденных фрагментов базы знаний (`R` L1143:C75972, L1143:C80438),
  `criteria` — к слову «критерии поиска» в переводе, `tolerance`/`Deviation` — к GD&T
  и атрибуту SVG.
* Исполнение и учёт прогона — локальные; принятие решений о содержимом задачи, оценке
  и повторах — на сервере.
* Постусловное сравнение отпечатков документов реально существует и работает только
  как проверка политики «read-only не меняет модель».

Вывод (inference, не доказано):

* Цикл «оценить → исправить → переоценить», вероятно, реализован на сервере: клиент не
  содержит ни счётчика итераций, ни порога, ни истории оценок, а все решения приходят
  командами. Это согласуется с отсутствием соответствующей лексики, но сервер недоступен,
  поэтому сам цикл не доказан.

Неизвестное:

* Формула, порог, число оценок и правило остановки на сервере; смысл значений `run.status`;
  содержимое `attempt`/`phase` фоновых задач.
* Внутренности .NET-моста (`resources/win-x64/MecAgent.dll`): как именно вычисляется
  `readOnly` и `unknownMembers`, и как строится отпечаток документов. Переход к нему найден,
  но сам компонент в этой задаче не разбирался.
* Поведение при реальном запуске: сеть, учётная запись и SolidWorks не использовались,
  поэтому статические выводы не подтверждены наблюдением.

### Что это меняет для нашего контракта

* Подтверждается решение держать оценку и лимиты локально и явно: у MecAgent этой логики
  в клиенте нет, а серверная часть непроверяема. Наш `goal.outcome` с фиксированными
  требованиями, весом и порогом остаётся нашим собственным контрактом, а не копией.
* Полезный примитив — постусловная проверка «проверяющая операция не изменила документ»
  по отпечатку до/после. У нас её роль выполняют read-only проверки в бюджете вызовов и
  запрет мутаций после stop; отдельный отпечаток документов стоит рассматривать как
  дополнительную проверку, а не как замену.
* Их подтверждение имеет дедлайн и терминальный отказ без автоповтора — это совместимо
  с нашими `awaiting_confirmation` и запретом автоповторов мутаций.
* Их `status` — непрозрачная строка, а причина завершения живёт в отдельном вызове. Наш
  типизированный `status` плюс отдельный `completion_reason` и независимый `verification`
  дают более строгий контракт; менять его под MecAgent не нужно.
* Неизвестный исход у них решается только сообщением пользователю и переподключением. Наше
  правило «неизвестный исход блокирует прогоны до перезапуска» строже и должно сохраниться.
